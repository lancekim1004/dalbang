# 서울 한 달 살기 숙소 예약 사이트 — 기획서 (PLAN)

> 이 문서는 "무엇을, 왜, 어떤 순서로" 만드는지 정리한 설계도입니다.
> 내용을 바꿀 때는 사용자와 먼저 상의하고, 맨 아래 "변경 기록"에 남깁니다.

---

## 0. 한 줄 요약

서울에서 30일 이상 머무는 외국인이 공유주택·단기임대 숙소를 **방 단위**로 검색하고
**예약 요청**을 보내면, 관리자가 **승인/거절**하고 결과를 **이메일**로 알려주는 사이트.
결제는 없음(나중에 끼워 넣을 수 있게 구조만 준비).

- 사이트 화면 언어: 영어 (나중에 한국어·일본어 등 추가 가능하게 설계)
- 설계 기준: 휴대폰 화면 우선 → 태블릿·PC로 넓힘
- 목표 수준: 포트폴리오 + 실제 출시 가능
- **비용 원칙: 0원.** 도메인을 사지 않고, 유료 서비스나 카드 등록이 필요한 서비스는 쓰지 않음

## 1. 기술 구성과 선택 이유

| 역할 | 선택 | 쉽게 말하면 | 선택 이유 | 무료 범위 |
|---|---|---|---|---|
| 웹사이트 뼈대 | **Next.js** (TypeScript) | 화면과 서버 기능을 한 프로젝트에서 만드는 도구 | 자료·예제가 가장 많음. 검색 노출(SEO)에 유리. Vercel과 궁합 최고 | 무료(오픈소스) |
| 디자인 | **Tailwind CSS** | 미리 만들어진 스타일 조각을 붙여 꾸미는 방식 | 휴대폰 우선 화면 만들기 쉬움. CSS 파일 관리 부담 적음 | 무료 |
| 데이터베이스·로그인·사진 저장 | **Supabase** | 엑셀 같은 표(DB) + 관리자 로그인 + 사진 창고를 한 번에 주는 서비스 | 화면에서 표를 직접 보고 고칠 수 있어 초보자 관리가 쉬움. 실제 DB(PostgreSQL)라 "날짜 겹침 금지" 같은 규칙을 DB가 직접 막아줌 | 무료(DB 500MB, 사진 1GB) — **1주일간 아무도 안 쓰면 일시정지**됨 → GitHub Actions(무료 자동 실행)로 3일마다 접속해 깨워둠 |
| 인터넷에 올리기(배포) | **Vercel** | 코드를 GitHub에 올리면 자동으로 사이트가 갱신됨 | 설정이 거의 없음. Next.js 만든 회사 서비스 | 무료(개인·포트폴리오용) |
| 이메일 발송 | **Gmail SMTP + Nodemailer** | 사이트 전용 Gmail 계정으로 메일을 대신 보내는 방식 | 도메인 없이도 **누구에게나** 메일 발송 가능 (Resend 등은 도메인이 없으면 내 메일로만 보낼 수 있음). Gmail이 직접 보내서 스팸함에 덜 빠짐 | 무료(하루 약 500통) — 사이트 전용 Gmail을 새로 만들어 사용 |
| 지도 | **Leaflet + OpenStreetMap** | 무료 오픈 지도 | 신용카드 등록 필요 없음(구글 지도는 카드 필요). 외국인에게 영어 지명 표시 가능 | 무료(트래픽 많아지면 MapTiler 무료키로 교체) |
| 스팸 방지 | **Cloudflare Turnstile** | "로봇이 아닙니다" 체크(대부분 자동 통과) | 무료, 개인정보 수집이 적음 | 무료 |
| 정해진 시간 자동 실행 | **Vercel Cron** | 하루 1번 "오래된 요청 만료", "오래된 개인정보 삭제" 실행 | Vercel에 기본 포함 | 무료(하루 1번) |
| 다국어 | **next-intl** | 화면 글자를 언어별 파일로 분리 | 지금은 영어 파일 하나, 나중에 파일만 추가 | 무료 |
| 코드 보관 | **GitHub** | 코드 저장소 + 변경 이력 | Vercel 자동 배포와 연결 | 무료 |
| 오류 감시(선택) | **Sentry** | 사이트에서 오류가 나면 알려줌 | 출시 후 문제를 빨리 발견 | 무료(월 5천 건) |

**총 비용: 0원.**
- 사이트 주소는 Vercel 무료 주소(예: `seoul-month-stay.vercel.app`)를 사용, 도메인은 구매하지 않음
- 모든 서비스는 무료 요금제 안에서만 사용하고, 카드 등록이 필요한 서비스는 쓰지 않음
- 나중에 실제 출시로 바꾸려면: 도메인 구입 → 메일을 Resend 등 도메인 메일로 교체 (코드는 메일 보내는 부분 한 곳만 바꾸면 되게 만듦)

### 포트폴리오 데모 표시
- 모든 화면 상단에 작은 안내 띠: "Portfolio demo — listings are sample data." (실제 숙소로 오해하지 않게)
- 샘플 숙소는 가상의 이름, 지도 위치는 동네 중심 근처로 표시

### 결제를 나중에 넣기 위한 준비 (지금은 만들지 않음)
- 예약 상태에 "결제 대기(awaiting_payment)", "결제 완료(paid)" 자리를 미리 정의만 해둠
- 예약할 때 금액 내역을 그대로 저장(가격 스냅샷) → 나중에 결제 금액으로 그대로 사용
- `payments`(결제) 표 설계만 문서에 남겨두고 실제로 만들지는 않음
- 승인 처리 코드를 한 곳에 모아서, 나중에 "승인 → 결제 링크 발송"으로 바꾸기 쉽게 함

## 2. 화면 목록과 화면 흐름

### 2-1. 사용자 화면 (영어)

| # | 화면 | 주소(예시) | 주요 내용 |
|---|---|---|---|
| U1 | 홈 | `/` | 서비스 소개, 검색창(지역·입주일·기간·가격), 추천 방 |
| U2 | 방 목록 + 지도 | `/rooms` | 조건 검색 결과 카드 목록. 휴대폰은 "목록 ⇄ 지도" 전환 버튼, PC는 좌우 나란히 |
| U3 | 숙소(건물) 상세 | `/listings/[id]` | 건물 소개, 사진, 위치, 공용시설, 이 건물의 방 목록 |
| U4 | 방 상세 | `/rooms/[id]` | 사진, 월 가격, 보증금, 관리비, 포함 항목, 예약 가능 달력, 날짜 선택 시 **총액 미리보기** |
| U5 | 예약 요청 | `/rooms/[id]/request` | 날짜·이름·이메일·국적·메시지 입력, 개인정보 동의 체크, 총액 확인 |
| U6 | 요청 완료 | `/booking/submitted` | 예약 번호 표시 (예: `SML-7K3Q9P`), "이메일을 확인하세요" 안내 |
| U7 | 예약 조회 | `/booking/lookup` | 예약 번호 + 이메일 입력 → 상태 확인(대기/승인/거절/취소) |
| U8 | 개인정보 처리방침 | `/privacy` | 수집 항목, 목적, 보관 기간, 해외 서버 이전, 삭제 요청 방법 |
| U9 | 이용약관 | `/terms` | 예약 요청은 계약이 아님, 취소 규정 등 |
| U10 | 자주 묻는 질문 | `/faq` | 보증금, 입주 절차, 비자 관련 일반 안내 |
| U11 | 오류 화면 | 404 / 500 | "페이지를 찾을 수 없어요" + 홈으로 버튼 |

| # | 화면 | 주소(예시) | 주요 내용 |
|---|---|---|---|
| A1 | 관리자 로그인 | `/admin/login` | 이메일 + 비밀번호 |

| A5 | 방 편집 | `/admin/rooms/[id]` | 가격·보증금·관리비·최소 기간, 사진, 공개/숨김 |

## 3. 데이터베이스 설계

> 표 = 엑셀 시트 하나, 칸 = 열이라고 생각하면 됩니다.
> 모든 표에는 `id`(고유번호), `created_at`(만든 시각), `updated_at`(고친 시각)이 기본으로 있습니다(아래 표에서는 생략).
> 금액은 모두 **원(KRW) 정수**로 저장합니다(소수점 없음).

### 3-1. `districts` — 지역(구·동네)

| 칸 | 형식 | 설명 |
|---|---|---|
| slug | 글자 | 주소용 이름 (예: `mapo`) |
| name_en | 글자 | 영어 이름 (예: Mapo-gu) |
| sort_order | 숫자 | 표시 순서 |

### 3-2. `listings` — 숙소(건물·집)

| 칸 | 형식 | 설명 |
|---|---|---|
| district_id | 연결 | 어느 지역인지 |
| type | 선택 | `sharehouse`(공유주택) / `studio`(원룸 단기임대) / `apartment` |
| title / description | 글자 | 제목·소개 (영어) |
| address_en | 글자 | 영어 주소 (상세 주소는 승인 후 메일로만 안내) |
| lat / lng | 숫자 | 지도 좌표 (공개 지도에는 약간 흐리게 표시해 정확한 위치 보호) |
| amenities | 목록 | 공용시설 (wifi, washer, kitchen 등) |
| nearest_station | 글자 | 가까운 지하철역 |
| is_published | 예/아니오 | 공개 여부 (숨기기 기능) |

### 3-3. `rooms` — 방 (예약 단위)

| 칸 | 형식 | 설명 |
|---|---|---|
| listing_id | 연결 | 어느 숙소의 방인지 |
| name | 글자 | 방 이름 (예: Room A, 2F) |
| room_type | 선택 | `private`(개인실) / `shared`(다인실 침대) / `entire`(집 전체) |
| monthly_price | 정수 | 월 가격 |
| deposit | 정수 | 보증금 (1회) |
| maintenance_fee | 정수 | 월 관리비 |
| min_nights | 정수 | 최소 숙박일 (기본 30, 30보다 작게 설정 불가) |
| max_guests | 정수 | 최대 인원 |
| size_m2 | 숫자 | 면적 |
| features | 목록 | 방 안 시설 (private bathroom, desk 등) |
| is_published | 예/아니오 | 공개 여부 |

### 3-4. `photos` — 사진

| 칸 | 형식 | 설명 |
|---|---|---|
| listing_id / room_id | 연결 | 둘 중 하나에 연결 |
| storage_path | 글자 | Supabase 사진 창고 안의 위치 |
| alt_text | 글자 | 사진 설명 (시각장애인 화면낭독·검색 노출용) |
| sort_order | 숫자 | 표시 순서 (첫 번째 = 대표 사진) |

### 3-5. `bookings` — 예약 요청

| 칸 | 형식 | 설명 |
|---|---|---|
| code | 글자 | 손님에게 보여줄 예약 번호 (예: `SML-7K3Q9P`, 추측 어렵게 무작위) |
| room_id | 연결 | 어느 방인지 |
| check_in / check_out | 날짜 | 입주일 / 퇴실일 (퇴실일 밤은 숙박에 포함 안 됨) |
| status | 선택 | 아래 "예약 상태" 참고 |
| guest_name / guest_email | 글자 | 손님 이름·이메일 |
| guest_phone | 글자 | 선택 입력 (WhatsApp 등) |
| nationality | 글자 | 선택 입력 |
| guests_count | 정수 | 인원 |
| message | 글자 | 손님 메시지 |
| price_snapshot | 묶음 데이터 | 요청 시점 금액 내역 전체 (월가·개월수·남은일수·일할금액·보증금·관리비·총액) |
| total_amount | 정수 | 총액 (검색·정렬용으로 따로 저장) |
| admin_note | 글자 | 관리자 메모 (손님에게 안 보임) |
| reject_reason | 글자 | 거절 사유 (손님 메일에 포함) |
| decided_at / decided_by | 시각 / 연결 | 언제, 어떤 관리자가 처리했는지 |
| privacy_consent_at | 시각 | 개인정보 동의 시각 |
| locale | 글자 | 손님이 사용한 언어 (`en`) — 메일 언어 결정용 |

**예약 상태(status)**

| 값 | 의미 | 지금 사용? |
|---|---|---|
| `pending` | 승인 대기 | ✅ |
| `approved` | 승인됨 (날짜 확정) | ✅ |
| `rejected` | 거절됨 | ✅ |
| `cancelled` | 승인 후 취소 | ✅ |
| `expired` | 관리자가 기한 내 처리 안 함 / 입주일 지남 | ✅ |
| `awaiting_payment` | 결제 대기 | ⏸ 결제 도입 시 |
| `paid` | 결제 완료 | ⏸ 결제 도입 시 |

### 3-6. `booking_events` — 예약 처리 기록

| 칸 | 형식 | 설명 |
|---|---|---|
| booking_id | 연결 | 어느 예약인지 |
| from_status / to_status | 선택 | 상태가 무엇에서 무엇으로 바뀌었는지 |
| actor | 글자 | `guest` / `admin:이메일` / `system` |
| note | 글자 | 메모 |

### 3-7. `admins` — 관리자 명단

| 칸 | 형식 | 설명 |
|---|---|---|
| user_id | 연결 | Supabase 로그인 계정 |
| email | 글자 | 관리자 이메일 |

> 로그인 계정이 있어도 이 명단에 없으면 관리자 화면에 들어갈 수 없습니다.

### 3-8. `email_logs` — 메일 발송 기록

| 칸 | 형식 | 설명 |
|---|---|---|
| booking_id | 연결 | 관련 예약 |
| type | 선택 | 접수/승인/거절/취소/관리자알림 |
| status | 선택 | `sent` / `failed` |
| error | 글자 | 실패 이유 (관리자가 "다시 보내기" 가능) |

### 3-9. (미래) `payments` — 결제 (지금은 만들지 않음, 설계만)

| 칸 | 형식 | 설명 |

| status | 선택 | 대기/완료/환불 |

### 3-10. 표 사이 관계

                    │                │                 └──── N email_logs

### 3-11. 데이터 보안 규칙 (Supabase RLS = 표마다 "누가 읽고 쓸 수 있나" 규칙)

## 4. 예약 규칙 상세

### 4-1. 날짜 기본 규칙
- 모든 날짜는 **서울 시간(Asia/Seoul)** 기준, 시각 없이 "날짜"만 다룸
- 숙박일수 = 퇴실일 − 입주일 (예: 3월 1일 입주, 3월 31일 퇴실 = 30박)
- 퇴실일 당일에는 다음 손님이 입주 가능 (3/31 퇴실, 3/31 입주 → 겹침 아님)

### 4-2. 요청 가능 조건 (하나라도 어기면 요청 불가 + 이유를 영어로 안내)

| 규칙 | 기준 | 손님에게 보이는 안내 (예시) |
|---|---|---|
| 최소 기간 | 숙박일수 ≥ 30 (방마다 더 길게 설정 가능) | "Minimum stay is 30 nights." |
| 날짜 순서 | 퇴실일 > 입주일 | "Check-out must be after check-in." |
| 과거 날짜 금지 | 입주일 ≥ 내일(서울 기준) | "Check-in must be from tomorrow." |
| 너무 먼 미래 금지 | 입주일 ≤ 오늘 + 12개월 | "You can request up to 12 months ahead." |
| 최대 기간 | 숙박일수 ≤ 365 | "Maximum stay is 12 months." |
| 공개된 방만 | 숙소·방 모두 공개 상태 | "This room is not available." |
| 인원 | 인원 ≤ 방 최대 인원 | "This room fits up to N guests." |
| 날짜 겹침 | **승인된(approved)** 예약과 겹치면 불가 | "These dates are already booked." |
| 중복 요청 | 같은 이메일 + 같은 방 + 겹치는 날짜의 대기 요청이 이미 있으면 불가 | "You already have a pending request." |
| 스팸 방지 | Turnstile 통과 + 같은 사람이 짧은 시간에 너무 많이 요청하면 차단 | "Too many requests. Try again later." |

> 대기(pending) 요청끼리는 날짜가 겹쳐도 됩니다. 여러 손님이 같은 날짜를 요청할 수 있고,
> 관리자가 그중 한 명을 고릅니다.

### 4-3. 총액 계산

```
총액 = 월 가격 × 개월 수
     + 하루 가격 × 남는 날짜 수
     + 보증금
     + 관리비 × 개월 수
```

- **개월 수**: 입주일부터 "같은 날짜"까지를 1개월로 셈 (달력 기준)
  - 3/15 → 4/15 = 1개월, 3/15 → 5/20 = 2개월 + 5일
  - 그 달에 같은 날짜가 없으면 그 달의 마지막 날로 맞춤 (1/31 → 2/28(윤년 2/29) = 1개월)
- **남는 날짜 수**: 개월 수를 빼고 남은 날 수
- **하루 가격** = 월 가격 ÷ 30 (원 단위 반올림)
- **보증금**: 1회만 더함 (퇴실 시 돌려받는 돈이라는 안내 문구 표시)
- **관리비**: 개월 수만큼만 곱함 (남는 날짜에는 관리비 없음)
- 계산은 서버에서 다시 한 번 함 (화면에서 보낸 금액은 믿지 않음)
- 계산 결과 전체를 예약에 저장(가격 스냅샷) → 나중에 관리자가 가격을 바꿔도 기존 요청 금액은 그대로

**계산 예시** (월 900,000원 / 보증금 500,000원 / 관리비 100,000원, 3/15 입주 → 5/20 퇴실, 66박)

| 항목 | 계산 | 금액 |
|---|---|---|
| 월세 | 900,000 × 2개월 | 1,800,000 |
| 남는 날짜 | 30,000 × 5일 | 150,000 |
| 관리비 | 100,000 × 2개월 | 200,000 |
| 보증금 | 1회 | 500,000 |
| **총액** | | **2,650,000** |

**주의할 예외**
- 2/1 → 3/1은 달력상 1개월이지만 28박이라 **최소 30박 규칙에 걸려 요청 불가**
- 1/31 → 3/2 (평년, 30박): 1/31→2/28 = 1개월, 남는 날짜 2일
- 화면 금액 표시: `₩2,650,000` (나중에 USD 참고 환율 표시 추가 가능)

### 4-4. 동시 요청 처리 (같은 방·같은 날짜에 여러 사람이 거의 동시에)

| 상황 | 처리 방법 |
|---|---|
| 두 손님이 동시에 요청 | 둘 다 `pending`으로 접수됨 (대기끼리는 겹쳐도 OK) |
| 관리자가 A를 승인 | DB가 "승인된 예약끼리 날짜 겹침 금지" 규칙으로 최종 확인 후 승인 |
| A 승인 시 겹치는 B, C 대기 요청 | **자동 거절** + "날짜가 이미 확정됨" 사유로 메일 발송 |
| 관리자 두 명이 동시에 A와 B를 승인 | DB 규칙 때문에 **먼저 처리된 하나만 성공**, 나머지는 "이미 겹치는 승인 예약이 있음" 오류 표시 |
| 손님이 요청하는 순간 다른 예약이 승인됨 | 요청 저장 직전 DB에서 다시 확인 → 겹치면 "These dates are already booked." |
| 같은 손님이 버튼을 여러 번 누름 | 버튼 잠금 + 중복 요청 규칙으로 한 건만 저장 |

> 핵심: "겹침 금지"를 화면 코드가 아니라 **데이터베이스 자체 규칙**(PostgreSQL 겹침 제외 제약)으로 걸어서,
> 어떤 경우에도 승인된 예약 두 개가 같은 날짜를 차지할 수 없게 합니다.

### 4-5. 상태 변화 규칙

```
pending ──승인──▶ approved ──관리자 취소──▶ cancelled
   │
   ├──거절──▶ rejected
   ├──다른 요청 승인으로 자동──▶ rejected
   └──3일간 미처리 or 입주일 지남──▶ expired
```

- 거절·취소·만료된 예약은 되돌릴 수 없음 (필요하면 손님이 새로 요청)
- 모든 상태 변화는 `booking_events`에 기록
- (결제 도입 시) `approved` 대신 `awaiting_payment` → `paid` 흐름을 끼워 넣음

### 4-6. 그 밖의 예외 상황

| 상황 | 처리 |
|---|---|
| 대기 요청이 있는 방을 관리자가 숨김 | 기존 요청은 유지, 관리자 화면에 경고 표시 |
| 승인된 예약이 있는 방을 삭제하려 함 | 삭제 금지, "숨기기"만 가능 |
| 관리자가 가격 변경 | 기존 요청 금액은 스냅샷 그대로, 새 요청부터 새 가격 |
| 메일 발송 실패 | 예약 처리는 그대로 완료, `email_logs`에 실패 기록 → 관리자 화면에 "다시 보내기" 버튼 |
| 예약 조회에서 번호·이메일 틀림 | "찾을 수 없음"만 안내 (어느 쪽이 틀렸는지 알려주지 않음 — 정보 보호) |
| 조회를 계속 틀림 | 일정 횟수 이상이면 잠시 차단 |
| 손님이 취소하고 싶음 | MVP에서는 메일로 관리자에게 연락 → 관리자가 취소 처리 (손님 직접 취소는 나중에) |

## 5. 출시 수준 체크 항목 (전 단계 공통 기준)

- **보안**: 비밀 키는 코드에 넣지 않고 환경변수로만 / DB 보안 규칙(RLS) / 관리자 페이지 접근 차단 / 입력값 검사 / 스팸 방지 / 요청 횟수 제한
- **오류 처리**: 모든 입력 오류는 손님이 이해할 영어 문장으로 / 404·500 화면 / 서버 오류는 Sentry로 기록
- **검색 노출(SEO)**: 페이지마다 제목·설명 / 공유 미리보기 이미지 / sitemap.xml·robots.txt / 숙소 구조화 데이터 / 관리자 페이지는 검색 제외
- **개인정보**: 처리방침 화면 / 요청 시 동의 체크 / 필요한 정보만 수집(여권번호 등 수집 안 함) / 보관 기간(퇴실 후 1년, 거절·만료 후 6개월) 지나면 삭제 / 해외 서버(Vercel·Google) 이용 사실 명시 (DB는 서울 지역)
- **접근성·속도**: 휴대폰에서 글자·버튼 크기 충분 / 사진 자동 최적화 / 화면낭독기용 설명
- **법적 안내**: 이 사이트는 "예약 요청 중개" 화면이며, 실제 숙소를 운영하려면 숙소 운영자가 관련 법(외국인관광 도시민박업 등) 기준을 갖춰야 함 — 실제 운영 전 확인 필요
